# Данные, согласия и персональные данные

Статус: черновик. Финальные формулировки политики персональных данных, согласий и ролей Сторон должны быть проверены юристом.

## 1. Принцип минимизации

Astor Butler собирает только данные, необходимые для обработки конкретной заявки гостя.

Запрещается:

- скрыто собирать телефон, email, Telegram username или иные контакты;
- передавать данные в Telegram, AI, Saby или сотруднику без понятного назначения;
- обещать передачу «всех персональных данных»;
- использовать данные для маркетинга без отдельного правового основания/согласия.

## 2. Категории данных

Может обрабатываться:

- Telegram chat id / external user id;
- имя, если гость указал его сам или оно доступно в канале законно;
- телефон, если гость передал его явно;
- email, если гость передал его явно;
- текст сообщений;
- дата/время/количество гостей;
- пожелания по столу/зоне;
- история статусов заявки;
- consent version, timestamp, source/channel.

Не обрабатывается без отдельного согласования:

- паспортные данные;
- платежные данные;
- биометрия;
- медицинские сведения;
- скрытая аналитика личности;
- данные третьих лиц, не участвующих в заявке.

## 3. Согласие гостя

В первом контакте Astor Butler должен кратко сообщить:

- кто обрабатывает заявку;
- зачем нужны данные;
- какие данные нужны для связи и бронирования;
- ссылка на политику персональных данных;
- что гость может продолжить без лишних данных, если сценарий это позволяет.

Для web/Yandex ID/Telegram contact sharing применяется отдельное явное действие пользователя. Phone/email/Telegram contact не должны извлекаться автоматически.

## 4. Коммерческие предложения и маркетинг

Email может использоваться для коммерческого предложения только если гость дал соответствующее согласие или есть иное подтвержденное правовое основание.

Согласие на обработку заявки и согласие на маркетинговую/коммерческую рассылку не должны смешиваться в одну скрытую галочку.

## 5. Передача данных оператору

Оператору/хостес передается минимальная карточка заявки:

- ID заявки;
- время;
- канал;
- текст или краткое резюме;
- дата/время/гости;
- контакт, если гость его предоставил;
- ссылка/идентификатор consent evidence;
- статус.

## 6. Передача данных в Saby

В Saby передаются только поля, необходимые для создания/проверки бронирования и разрешенные API-контрактом, политикой и согласием гостя.

Перед подключением Saby нужно определить:

- правовую роль Saby и Заказчика;
- является ли Saby самостоятельным оператором, обработчиком или сервисом Заказчика;
- где физически хранятся данные;
- сроки хранения;
- порядок удаления/исправления;
- перечень обязательных и необязательных полей.

## 7. Передача данных в AI/STT/TTS

AI/STT/TTS провайдеры получают только минимальный контекст, необходимый для классификации, нормализации или ответа.

Секреты и ключи провайдеров хранятся server-side. В frontend они не передаются.

Для голосовых сообщений требуется:

- явный клик на микрофон;
- отображение состояния записи;
- возможность отмены;
- HTTPS secure context;
- server-side обработка STT/TTS;
- политика хранения/удаления аудио.

## 8. Хранение и удаление

Стороны должны согласовать:

- срок хранения сообщений;
- срок хранения заявок;
- срок хранения consent audit;
- порядок удаления по запросу;
- кто имеет доступ к данным;
- формат выгрузки данных;
- резервное копирование и уничтожение backup.

## 9. Журнал аудита

Astor Butler должен сохранять:

- ID согласия;
- версию политики;
- timestamp;
- source/channel;
- user/session id;
- действие пользователя;
- ID заявки, к которой относится согласие.

## 10. Открытые юридические переменные

- финальная политика персональных данных;
- оператор/обработчик персональных данных;
- договор поручения обработки, если нужен;
- место хранения данных;
- срок хранения;
- порядок трансграничной передачи, если внешние сервисы это затрагивают;
- согласие на коммерческие предложения;
- контакты ответственного за персональные данные.
