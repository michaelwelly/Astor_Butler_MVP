# Техническое задание Astor Butler для ресторана/площадки

Статус: черновик для согласования. Конкретный ресторан, бренд, каналы, SLA, стоимость и ответственные лица заполняются Сторонами.

## 1. Цель

Создать управляемого цифрового ассистента Astor Butler, который помогает гостю пройти путь от первого сообщения до структурированной заявки на бронирование или обращения к команде ресторана.

Ассистент должен:

- принимать сообщения гостя в Telegram и иных согласованных каналах;
- сохранять историю диалога и состояние FSM;
- уточнять дату, время, количество гостей, пожелания и контакт;
- показывать гостю согласованную информацию ресторана;
- передавать заявку уполномоченному сотруднику;
- поддерживать confirmation-gated бронирование;
- готовить техническую границу для Saby-интеграции.

## 2. Текущая реализация Astor Butler

В проекте уже есть:

- Spring Boot backend на Java 21;
- FSM как source of truth для сценариев;
- PostgreSQL для заявок, сообщений, статусов и audit trail;
- Redis для runtime state/drafts;
- Telegram transport boundary;
- table booking domain:
  - `venue_tables`;
  - `table_reservation_orders`;
  - `table_reservation_holds`;
  - local availability;
  - local holds;
  - hostess confirmation;
  - `sbis_external_id` как поле для будущей внешней синхронизации;
- REST endpoints `/api/bookings/**` для tables/availability/reservations/confirm/reject;
- документация `docs/fsm/TABLE_BOOKING.md`.

## 3. Каналы

Базовый канал:

- Telegram bot для гостя.

Дополнительные каналы по отдельному согласованию:

- web chat на сайте;
- Telegram admin/operator chat;
- voice input через SpeechKit STT/TTS;
- CRM/admin cockpit;
- email/SMS/push.

## 4. Сценарии гостя

### 4.1. Первичный контакт

Гость пишет сообщение свободным текстом. Astor Butler:

- фиксирует сообщение;
- проверяет согласие/правовое основание;
- классифицирует намерение через правила/FSM/AI;
- выбирает сценарий;
- не переводит гостя в бизнес-сценарий до необходимых согласий и контактов.

### 4.2. Запрос доступности

Пример: «Есть стол завтра в 20:00 на двоих?»

Astor Butler:

- нормализует дату/время/количество гостей;
- проверяет локальную доступность или, после интеграции, внешний статус Saby;
- возвращает кандидаты или просит уточнить вводные;
- не создает финальную бронь без подтверждения.

### 4.3. Подбор стола

Пример: «Хочу тихий стол у окна».

Astor Butler:

- использует локальную модель зала и правила вместимости;
- предлагает подходящий вариант, если данных достаточно;
- передает выбор сотруднику или внешней системе только после подтверждения гостя.

### 4.4. Создание заявки

Astor Butler создает локальную заявку и hold, когда собраны минимальные данные:

- дата;
- время;
- количество гостей;
- контакт или согласованный способ обратной связи;
- пожелание/зона/стол, если указаны.

Финальное подтверждение выполняет сотрудник Заказчика или согласованный external workflow.

### 4.5. Изменение и отмена

Astor Butler:

- ищет активные заявки гостя;
- просит явное подтверждение изменения/отмены;
- сохраняет историю решения;
- синхронизирует внешний статус после подключения Saby.

## 5. AI и голос

AI используется только как вспомогательный слой:

- классификация намерения;
- нормализация текста;
- резюме для оператора;
- черновик ответа.

AI не подтверждает бронирования, платежи, скидки, юридические обязательства или спорные действия.

SpeechKit STT/TTS подключается только после наличия HTTPS, server-side credentials, тестового бюджета, лимитов, согласий и успешного smoke test.

## 6. Уведомления команде

Уведомление должно содержать:

- ID заявки/диалога;
- канал;
- время;
- имя/контакт, если предоставлен с согласием;
- исходный текст гостя;
- нормализованные дата/время/гости;
- выбранный стол/зона, если есть;
- статус;
- кнопки или инструкции подтверждения.

Не допускается скрытая передача данных, не связанных с заявкой.

## 7. Нефункциональные требования

- хранение секретов только в runtime env/secret storage;
- rate limiting для chat/LLM/Telegram chain;
- timeouts и circuit breakers для внешних API;
- graceful fallback при сбоях Saby/Telegram/AI;
- audit trail для сообщений, согласий и статусов;
- возможность rollback;
- тесты для сценариев бронирования, отказов, недоступности внешних сервисов и повторных запросов.

## 8. Ограничения

До получения подтвержденного Saby API Astor Butler работает с локальной моделью зала и подтверждением сотрудника. Это не должно называться живой Saby-интеграцией.

Любое автоматическое создание, изменение или отмена брони во внешней системе разрешается только после:

- подтвержденного API-контракта;
- тестового окружения;
- idempotency policy;
- acceptance tests;
- письменного согласования Заказчика.
